# Комнаты и Discord Rich Presence

Репозитории и общие контракты описаны в [карте архитектуры](https://github.com/Blockfield/blockfield-workspace/blob/main/docs/ARCHITECTURE.md).

## Приложение Blockfield

Application ID: `1548300877125779456`. Он встроен в лаунчер; для обычной сборки дополнительная настройка не нужна. Для другого приложения можно задать `BLOCKFIELD_DISCORD_APPLICATION_ID` и зарегистрировать соответствующую схему `discord-<ID>` в `tauri.conf.json`.

В Developer Portal сохранены ассет `blockfield` (логотип 1024×1024) и обложка приглашения. Визуализатор портала служит только примером и не настраивает работающий клиент.

## Создание другого приложения Discord

1. Откройте https://discord.com/developers/applications и войдите в Discord.
2. Нажмите **New Application**, укажите **Blockfield**, подтвердите создание.
3. На странице **General Information** скопируйте **Application ID**. Это публичный числовой идентификатор. Создавать бота, выдавать OAuth-разрешения и копировать Client Secret не нужно.
4. В GitHub-репозитории исходников лаунчера откройте **Settings → Secrets and variables → Actions → Variables → New repository variable**.
5. Имя переменной: `BLOCKFIELD_DISCORD_APPLICATION_ID`. Значение: скопированный Application ID.
6. Соберите новую версию лаунчера обычным процессом релиза. Workflow `Launcher Release` уже передаёт переменную в сборку Windows и Linux. Изменение GitHub-переменной не меняет установленные лаунчеры: игрокам нужна новая сборка.

Локально можно передать `BLOCKFIELD_DISCORD_APPLICATION_ID` через `.env` в корне лаунчера либо окружение перед сборкой. Не добавляйте локальные `.env` в Git. Для AppImage/установщика идентификатор встраивается при компиляции; во время разработки доступен также из окружения.

## Проверка Discord

Запустите настольный Discord и новый лаунчер. В настройках Discord разрешите отображение игровой активности, а в настройках лаунчера включите **Discord Rich Presence** и сохраните настройки. Обновление происходит каждые 10 секунд.

Проверяйте собственный статус с другого аккаунта: Discord может не показывать владельцу кнопки его активности. Ожидаемые состояния: «В лаунчере», «Запускает игру», «В главном меню», «В лобби», карта и состояние текущего матча. В официальном настольном Discord в лобби и доступной комнате появляются нативные приглашения. Отправьте приглашение через кнопку «+» в чате Discord; друг принимает его кнопкой «Присоединиться». Лаунчер открывается и выбирает лобби или конкретную комнату. Если он уже запущен, используется его единственный экземпляр. На заполненном сервере приглашения не публикуются.

Лаунчер подписывается на `ACTIVITY_JOIN`. Если Discord-клиент не подтверждает подписку (в частности, arRPC в проверенном Vesktop 1.6.7), активность содержит обычную кнопку со ссылкой на сайт. Её можно открыть и отправить адрес другу. Сайт передаёт приглашение лаунчеру через `blockfield://join/<цель>`. Функциональность сторонних клиентов может отличаться. Отсутствие Discord не мешает запуску игры.

Статус матча доступен, когда игру запускает фирменный лаунчер с обновлённым клиентским модом. При запуске через Prism эта интеграция лаунчера не работает. Встроенный переключатель отключает передачу активности. Бот и сервер Discord для работы интеграции не требуются.

Официальная документация: https://docs.discord.com/developers/platform/rich-presence и https://docs.discord.com/developers/topics/rpc.

## Контракт комнат

Серверный мод добавляет поле `blockfield` в стандартный Minecraft Server List Ping:

```json
{
  "checkedAt": 1789214400000,
  "rooms": [
    {
      "id": "12345678-1234-1234-1234-123456789abc",
      "name": "Комната 1",
      "mode": "Захват точек",
      "map": "Карта",
      "phase": "GAME",
      "players": 4,
      "joinable": true
    }
  ]
}
```

`checkedAt` — время снимка в миллисекундах Unix. ID — UUID конкретной комнаты; номер комнаты остаётся только видимым названием и аргументом административных команд. Закрытая комната не может быть случайно заменена другой по старой ссылке. Фазы: `IDLE`, `VOTING`, `PREPARING`, `GAME`, `MATCH_END`. Снимок создаётся в игровом потоке раз в секунду, сетевой поток читает копию. Данные старше 30 секунд считаются недоступными.

Лаунчер каждые 10 секунд запрашивает `/api/rooms` у сайта и отдельно делает ping публичного адреса из `launcher.json.server`. Сайт читает расширение SLP внутреннего игрового сервера через `BLOCKFIELD_SERVER_HOST/PORT`, а доступность публичного прокси — через `BLOCKFIELD_LOBBY_HOST/PORT`. Параллельные запросы объединяются, кэш живёт 5 секунд. В текущем Velocity `ping-passthrough` выключен, поэтому комнаты получают через внутренний игровой адрес. Дополнительный HTTP-порт игровому серверу не нужен.

Ответ `/api/rooms` содержит `available`, `checkedAt`, `rooms` и необязательные `build`, `lobby`, `online`, `maintenance`. Комната может дополнительно передавать `battle`, `format`, `admission`, `ready`. Host-controller задаёт режим через `BLOCKFIELD_GATE_FILE`; во время техработ сайт скрывает комнаты, а лаунчер показывает причину недоступности.

Ссылка `blockfield://join/<UUID>` или `blockfield://join/lobby` открывает единственный экземпляр лаунчера. В ней нет адресов серверов, путей, команд или токенов. Прочие форматы отклоняются. Windows регистрирует протокол при установке; Linux — при запуске релизной сборки. Для Linux сначала запустите лаунчер из постоянного расположения. В отладочной сборке системная ассоциация намеренно не заменяется.

Выбор сохраняется в памяти лаунчера при переходе к установке/обновлению. После завершения подготовки нажмите «Играть» на экране обновления: клиент подключится к серверу и передаст обычное действие входа в комнату или возврата в лобби. Если игра уже работает, запрос передаётся ей; сервер сохраняет обычные правила входа и показывает меню, если комната закрылась. Запрос действует 10 минут и обрабатывается только на сервере из настроек сборки. Закрытие лаунчера отменяет неисполненный выбор.

Лаунчер атомарно записывает `room-request.json` с полями `room` и `createdAt` в свой каталог данных. Клиент получает путь через `BLOCKFIELD_BRIDGE_DIR` и разрешённый адрес через `BLOCKFIELD_SERVER`; `LauncherBridge` отправляет серверу `join:<UUID>` или `leave`. Статус для Rich Presence возвращается через `game-presence.json`. Клиент, запущенный напрямую для разработки, управляется средствами [workspace](https://github.com/Blockfield/blockfield-workspace/blob/main/docs/DEVELOPING.md).

## Выпуск изменений

1. Подготовить серверный и клиентский моды в [Blockfield/blockfield-mod](https://github.com/Blockfield/blockfield-mod); игровые проверки выполнить в workspace.
2. Обновить пины в [blockfield-client](https://github.com/Blockfield/blockfield-client) и [blockfield-server](https://github.com/Blockfield/blockfield-server), проверить совместимость. Общие моды требуют парного выпуска, сервер первым; тег и прод-деплой запускаются после явного подтверждения владельца.
3. Выпустить сайт из `Blockfield/blockfield-site` (бывший `blockfield-web`). Его `/api/rooms` должен маршрутизироваться в Astro так же, как `/`.
4. Задать Discord Application ID и выпустить лаунчер.

Старый сервер или недоступный статус показываются как «Список комнат недоступен», а не как пустой список или ноль игроков. Для собственного приложения Discord идентификатор встраивается в очередной обычный выпуск лаунчера.

## Приёмочная проверка приглашений

1. Обновите лаунчер и модпак на обоих компьютерах. Запустите настольный Discord, включите отображение активности и Rich Presence в лаунчере.
2. Первый игрок входит в лобби. Отправьте второму игроку приглашение из Discord. При закрытом лаунчере принятие должно запустить его и подключить к лобби.
3. Первый игрок входит в комнату и отправляет новое приглашение. Второй принимает его при работающей игре: он должен попасть в ту же комнату.
4. Примите приглашение в лобби, находясь в матче: игрок возвращается в лобби. Из главного меню игры приглашение начинает подключение; при игре на другом сервере подключитесь к Blockfield вручную, чтобы не прерывать чужую сессию.
5. Закройте комнату и примите старую ссылку: сервер сообщает, что комнаты уже нет, и не выбирает другую вместо неё.
6. Отключите Rich Presence и сохраните настройки: активность должна исчезнуть. Включите снова или перезапустите Discord: соединение восстанавливается.

Для проверки нативных приглашений нужен второй аккаунт. Сам себе пользователь приглашения не видит. Автоматические тесты проверяют IPC, фрагментацию сообщений, допустимые цели и устаревание запросов; они не заменяют проверку интерфейса Discord с двумя аккаунтами.
